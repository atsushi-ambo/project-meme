# プロジェクト・メメ

メメの動画・鳴き声と前後の状況を記録し、声・行動、その後の様子、予想を積み重ねるローカルアプリ。「メメ辞書」と体調日記を同じ画面から利用できます。Python・API・PostgreSQLの学習を兼ねています。

## 起動

Docker実行環境が必要です。Python・PostgreSQL・依存ライブラリはDocker内で動きます。設定作成とバックアップのスクリプトだけMacBookの標準Pythonで実行します。

```sh
cd ~/personal/app/project-meme
python3 scripts/setup.py
docker compose up -d --build
```

[http://localhost:8000](http://localhost:8000) を開きます。DBの準備とマイグレーションの後にアプリが起動します。

```sh
docker compose stop                  # 停止。データは残る
docker compose up -d                 # 再起動
docker compose logs --tail=50 web    # エラーの確認
```

`.env`は自動生成され、既存の設定は上書きしません。秘密値をGitへ入れないでください。通常の停止に`docker compose down -v`は使いません。`-v`はDBの保存領域も削除します。

## 使い方

1. iPhoneで撮影したファイルをAirDropでMacBookへ移します。ProResはオフ、HEVC撮影を想定しています。
2. ファイルを `~/Movies/project-meme/inbox/` などへ置きます。写真アプリへの登録は不要です。
3. 「声・行動を記録」から本文・日時・状況を保存します。
4. 詳細画面で添付を選んで保存します。撮影日時が不明なら空欄にできます。
5. 前後の出来事やメメの反応は同じメモにまとめます。書き足す場合は「編集する」から更新します。予想は任意で複数選べます。

対応する取り込み形式は、HEVC/H.264のMOV・MP4、JPEG・PNG、M4A・MP3・WAVです。HEICとProResは初版では受け付けません。HEVCの再生はブラウザ・端末に依存し、再生できない場合は原本をダウンロードできます。実際のiPhoneのMOV（約279MB）は保存とChromeでの映像読み込みを確認済みです。HDRの色・音声・全編の目視再生は未確認です。MOVの拡張子は変更せず、そのまま選択してください。

空のDBへ明示した架空のサンプルを追加するには次を実行します。既存記録がある場合は追加しません。

```sh
docker compose exec web python -m app.demo
```

サンプルには「サンプル」と表示します。体重等はメメの実測値ではありません。実データ利用前に画面から削除できます。

## 保存と設定

- コード：`~/personal/app/project-meme/`（Git管理）
- 取り込み元：`~/Movies/project-meme/inbox/`（アプリからは変更しない）
- アプリの添付：`~/Movies/project-meme/media/`（Dockerへ接続）
- 一時ファイル：`media/staging/`
- PostgreSQL：Dockerの`project-meme_postgres`ボリューム

アプリはファイルをコピーします。取り込み元・バックアップは別に容量を使います。非公開リポジトリでも実動画・写真・DBをGitHubへ上げません。

`.env`で次の初期値を変更できます。変更後は`docker compose up -d`で反映します。

| 設定 | 初期値 | 内容 |
|---|---:|---|
| MAX_FILE_BYTES | 1000000000 | 添付1件の上限（1GB） |
| MAX_TOTAL_BYTES | 30000000000 | 保存・予約・削除待ちの合計（30GB） |
| RETENTION_DAYS | 60 | 新規添付の保存期間 |
| PORT | 8000 | localhostのポート |
| MEDIA_DIR | セットアップ時に設定 | 添付の保存先 |

一つの記録の添付は10件まで。動画は期限なしで保存し、写真・音声は53日目（期限の7日前）から案内し、期限を過ぎると非表示にして削除します。「残す」は期限対象外ですが容量には含まれます。起動時と約60秒ごとに期限と失敗を確認し、停止中の処理は次回起動後に行います。本文は残ります。削除失敗は管理画面へ表示し、再試行します。

`MEDIA_DIR`の変更だけでは既存ファイルは移動しません。保存先変更時はアプリを止めてデータも移してください。iPhoneの原本を整理する前に保存・再生・必要なバックアップを確認してください。

## 更新（ローカルへの反映）

GitHubのPRとmainへのpushで、隔離したPostgreSQLを使うテストとHTTPサーバーの起動確認、Python依存とアプリ・DBコンテナのOSの脆弱性検査が自動実行されます。MacBookへの反映は次の手順で行います。GitHubからMacBookへ自動接続する仕組みは設けていません。

```sh
git switch main
git pull --ff-only
python3 scripts/update.py
```

`update.py`一つで **テスト → Python監査 → 新イメージ作成 → アプリ・DBのOS監査 → バックアップ → DBイメージ更新 → DB構造更新 → 起動・DB接続確認** を行います。チェックアウト済みのコミットを反映し、未コミットの変更があれば拒否します。初回起動用ではなく、起動中のアプリの更新用です。更新中はバックアップ開始から短時間利用できなくなります。同時にバックアップ・復元・別のCompose操作を実行しないでください。更新コマンド同士の同時実行はロックで拒否します。

- テスト・監査・ビルド失敗：稼働中のアプリはそのままです。
- バックアップ失敗：元のアプリを再開します。途中のバックアップは復元に使いません。
- DBイメージ・DB構造の更新開始後の失敗：アプリを止め、バックアップを残します。互換性が不明な旧コードへの切り戻しやDBの自動上書きは行いません。以下の復元手順で別環境へ復元して確認します。

更新時のバックアップも通常と同じ保存先です。`update.json`にコミット・旧イメージ・更新段階を記録します。元のイメージには`project-meme:before-日時-識別子`タグを残します。バックアップ・旧イメージは自動削除しません。正常完了後は通常の`docker compose up -d`でも更新したイメージが使われます。

CIでは各失敗段階・起動確認に加え、テストDBを実際にダンプし、別DBへ復元するところまで検証します。GitHubの現在のプランでは必須チェックによるマージ制限を設定できないため、PRのCIとSecurityの成功を確認してからマージする運用です。

## バックアップと復元

MacBook内の別フォルダへ手動保存する初期方式です。本体故障に備える外部保存先と保持期間は未決定です。自動で古いバックアップを消しません。

```sh
python3 scripts/backup.py backup
```

アプリを一時停止し、DBダンプとメディアを `~/Library/Application Support/project-meme/backups/日時/` へ保存します。元々起動していたアプリは終了後に再開します。体調CSVやGitHubはバックアップの代わりになりません。

復元は既存環境を上書きせず、新しいDockerプロジェクトへ行います。

```sh
python3 scripts/backup.py restore '/バックアップの絶対パス' \
  --project meme-restore-check \
  --destination "$HOME/Movies/project-meme/restore-check"
```

復元先は [http://localhost:8002](http://localhost:8002)。同名の環境・保存先がある場合は拒否します。復元先の`restore.env`にも秘密値があるのでGitへ入れないでください。容量には復元先のDB・メディア分も必要です。

## セキュリティと利用範囲

初版はMacBookのlocalhost限定・ログインなしです。同じMacBookの利用者やローカルプロセスからデータを隔離しません。iPhoneからLAN経由で直接使う前に認証・認可・セッション保護を追加します。ポートの公開範囲を勝手に広げないでください。

Host/Origin検証、署名Cookieと照合するCSRFトークン、入力検証、パラメータ化SQL、HTMLエスケープ、CSP、受信容量・時間制限、ファイル内容検証を実装しています。添付は生成名で保存し、アプリ経由で配信します。DB接続権限は通常操作とマイグレーションで分けています。

2026-10-02指定の共通セキュリティ方針を適用し、[Webアプリケーションセキュリティ入門](https://bogus.jp/webapp_security_review.pdf)は参考資料として扱います。教材の固定バージョンや認証実装をそのままコピーする方針ではありません。検査の成功を安全の保証とは扱いません。

## 検証

テスト専用の別PostgreSQLと一時メディアを使用します。`.env`や個人のメディアを読み込まず、通常の記録は変更しません。次のコマンドが最新コードをビルドし、毎回固有の環境でテストして、成功・失敗にかかわらずテスト用DBを片付けます。Pythonは標準ライブラリだけを使い、追加インストールは不要です。PRとmainへのpush時も同じコマンドがGitHub Actionsで動きます。

```sh
python3 scripts/test.py
```

確認済み：記録の保存・編集・再送、辞書と合図、反応の後日追記、体調CSVと数式注入対策、CSRF/Origin/Hostの拒否、容量・パス・偽装ファイルの拒否、期限と「残す」、削除失敗の再試行、予約失効、全データ出力・全削除、生成HEVCの取り込みと部分配信。テスト結果と手動検証の詳細は開発説明を参照してください。

静的チェックはQualityワークフローで自動実行します。`pyproject.toml`にruff（構文・未定義名・import）、mypy（観測・画面共通・ルーターから段階導入）、coverage（床60%）の設定を置き、PRではTests・Security・Container security・secret-scanと合わせてすべて成功してからマージします。`automerge`ラベルの自動マージ対象にもQualityを含めます。

各リクエストには推測できないリクエストIDを付け、レスポンスの`X-Request-ID`と1行JSONのアクセスログ（`meme.http`）へ同じIDを記録します。本文や個人データはログへ出しません。障害時は画面のエラーとログをこのIDで結びつけます。本文検索は部分一致のまま、pg_trgmのGINインデックスで高速化しています（日本語の形態素解析はしません）。

未確認：実際のiPhone動画の4K・120fps/HDR再生と向き、iPhone/iPad実機操作、長期間の運用、1GB上限付近の実ファイル。容量は実ファイルと空き容量を確認して調整します。

意図の自動推定・pgvector、再生用の動画変換、ブラウザ内撮影、LANログインは後続です。比較資料の画面とJSONは利用できます。アプリは外部AIへ自動送信しません。

撮影日時はMOV/MP4の埋め込み情報から保存時に自動取得します。手入力があればそちらを優先し、情報がない・不正な場合は「不明」のまま保存します。保存後は添付の「撮影日時を修正」から変更できます。日時入力は日付・時・分を分け、日本時間の24時間表示と「今の日時」ボタンを用意しています。本文の出来事の日時は別に管理します。


声・行動の文章入力はメモ一つです。伝えたかったことの予想は別に複数選べ、予想ごとに「合っていそう・合わなそう・まだ分からない」を選べます。場所は「家のどこ？」から選択できます。


「保存管理 → アプリの写真とアイコン」から、ホーム・ヘッダー・ブラウザタブの写真を変更できます。JPEG/PNG（10MBまで）に対応します。HEICはMacのプレビューでJPEGへ書き出してから選択してください。表示用画像は `~/Movies/project-meme/media/profile.jpg` に保存し、GitHubには含めません。添付の期限削除とは別に保持し、写真を外す操作または全記録削除で削除します。全データ出力・バックアップには含まれます。


観察の文章入力は「そのときの様子・前後のメモ」一つにまとめています。前後の出来事、自分がしたこと、メメの反応を続けて書けます。あとから書き足す場合も「編集する」で同じメモを更新します。記入例は入力欄の外に表示し、記録としては保存しません。以前の別欄の補足は読み取り用に残しています。

添付の送信が切れた場合は、同じファイルで「保存」を再試行できます。処理済みなら重複保存せず、失敗した予約は新しい予約でやり直します。送信中のファイル・撮影日時の選び直しはできません。途中でアプリが停止した場合、再送はファイルの先頭から行います。

## Codexに話して投稿する

「ダウンロードのIMG_1234.MOVと、今話したメモを投稿して」のように、動画の場所・出来事の日時・メモをCodexへ伝えられます。Codexが言い直しや重複を整理し、観察と予想を区別して保存します。アプリからの投稿・編集も引き続き使えます。MacBookでアプリが起動している必要があります。

投稿はローカルHTTP APIを通り、ブラウザと同じ入力検証・CSRF・容量制限・ファイル検証を受けます。動画は元ファイルからアプリの保存先へコピーされます。動画ファイル自体を外部AIへ送る処理は追加していません。音声の文字起こし・文章整理はCodexの会話で行います。

開発用の入口は `scripts/post.py` です。下書きはリポジトリ外の `~/Library/Application Support/project-meme/drafts/` に保存します。例（架空データ）：

```json
{
  "kind": "observation",
  "entry": {
    "submission_key": "13767979-dc48-4616-8df7-c98ee3c065e9",
    "occurred_at": "2026-10-06T19:30:00+09:00",
    "location": "仕事部屋",
    "description": "仕事中、メメがおもちゃをくわえてきて鳴いた。立ち上がると走って離れた。遊びたいのかもしれないが、理由は分からない。"
  },
  "media": [{"path": "/動画の絶対パス/IMG_1234.MOV"}]
}
```

```sh
python3 scripts/post.py '/下書きの絶対パス.json'           # 確認のみ
python3 scripts/post.py '/下書きの絶対パス.json' --submit  # 保存
```

新規投稿には新しいUUIDを使います。同じ内容の再試行は同じJSONで行うと、本文・保存済み添付を重複登録しません。本文と添付は別々に保存するため、添付の失敗後も本文は残ります。添付は省略可能。`kind: health`と体調入力の項目でも投稿できます。ポートを変えた場合は`--port`を指定します。日時や本文を変更して同じキーで送ると409で拒否されます。既存記録全体の編集はアプリから行い、末尾への追記はCodexからも行えます。


### 同じメモへその後の様子を追記する

「この記録に、撫でると鳴きやんで横に座ったことを追記して」のように、記録とその後の様子をCodexへ伝えられます。既存の「そのときの様子・前後のメモ」の末尾へ書き足します。別の投稿や入力欄は増やしません。アプリの「編集する」も引き続き使えます。

開発用には、まず読み取り専用のコマンドで本文と版番号を確認します。

```sh
python3 scripts/append.py --show 123
```

追記の下書きは、次の4項目だけを指定します。以下は架空の例です。`observation_id`と`expected_revision`には、実際に確認した記録のIDと版番号を入れます。下書きの保存場所と権限は新規投稿と同じです。

```json
{
  "observation_id": 123,
  "operation_key": "ac941868-351d-4901-9a10-8fbfb1274ba9",
  "expected_revision": 1,
  "text": "その後、撫でると鳴きやんで横に座った。理由はまだ分からない。"
}
```

```sh
python3 scripts/append.py '/追記の下書きの絶対パス.json'           # 確認のみ
python3 scripts/append.py '/追記の下書きの絶対パス.json' --submit  # 追記
```

追記ごとに新しい`operation_key`を発行し、通信が途切れた場合は同じ下書きで再試行します。保存済みなら二度書き足しません。同じキーで内容を変更すると409で拒否します。確認後にメモが編集されていた場合も409で止め、現在の内容を見直してから進めます。版番号を自動で差し替えて再送しません。追記の前に空行を入れ、メモ全体は1万文字以内です。

アプリの編集画面も、開いた時点の版番号を送ります。別の画面やCodexで先に更新された場合は、入力した文章を残して上書きを止めます。「保存済みの記録を確認」のリンクから最新メモを開き、新しい編集画面で自分の文章とまとめ直してから保存してください。

### 比較に使いたい動画を残す

動画は標準で期限なしです。写真・音声は投稿時に「残して」と明示すると、下書きの添付に`"keep": true`を付け、60日の期限削除から除外できます。容量上限には含まれます。media内の添付一件の架空の例：

```json
{"path": "/動画の絶対パス/IMG_1234.MOV", "keep": true}
```

`keep`を省略した再送は、アプリで変更済みの保管設定を保持します。`true`は残す指定、`false`は通常の期限へ戻す指定で、同じ値を再送しても反転しません。解除しても保存期限は延長されず、既に期限を過ぎていれば次の整理で削除される場合があります。期限切れで残す指定のない添付や、削除中・削除済みの添付は復活させません。

既存の動画も、対象を指定してCodexに保管設定の変更を頼めます。Codexは記録の添付IDを確認し、ローカルの`POST /api/media/{id}/keep`へ`{"keep": true}`または`{"keep": false}`を送ります。ユーザーが指定した動画だけを変更し、保存管理画面からも従来どおり操作できます。

## 週の振り返り

メニューの「週の振り返り」で、日本時間の今日までの7日間を確認できます。最終日を変更するか、前の7日間へ移動して過去の記録も見返せます。日別の記録数、場所・状況タグ、予想ごとの「合っていそう／合わなそう／まだ分からない」、体調の記録を元の記録へのリンク付きで表示します。

件数は投稿した記録の件数です。鳴いた実際の回数や、未記録の体調が正常だったことを表しません。架空のサンプルと削除中の記録は対象外です。DB更新で旧サンプルの先頭マーカーを専用フラグに移行し、メモの編集後もサンプルとして除外します。

「この1週間を振り返って」とCodexに伝えると、次の読み取りコマンドから実記録を取得して、共通する状況・反対の例・まだ分からないことを整理できます。文章には根拠の記録リンクを付け、飼い主の予想を正解として扱いません。アプリの画面はDBに基づく集計で、外部AIへ自動送信しません。

```sh
python3 scripts/review.py
python3 scripts/review.py --end 2026-10-06
```

下書きJSONに `"guesses": ["preset:attention"]` を追加すると、Codex投稿でも「かまってほしい」を予想欄へ登録します。値はplay／food／attention／door／follow／concern／unknown、既存辞書は`item:ID`です。ユーザーが話した予想だけを選び、初期の関係は「まだ分からない」です。再送しても重複せず、アプリで付けた評価は保持します。


## 選んだ記録を比較する

「声・行動」の一覧で1〜5件を選び「選んだ記録を比べる」へ進むか、詳細の比較リンクを使います。全文メモ、日時・場所・タグ、予想と飼い主の評価、以前の補足、動画・音声・写真を出典付きで並べます。サンプル・削除中の記録は対象外です。メモの入力項目は増えません。

Codexには「記録123と124で、似ている状況と違う反応を比べて」のように頼めます。ローカルでコマンドを実行できる別のアシスタントも、同じJSONを読めます。IDは架空の例です。

```sh
python3 scripts/analyze.py --ids 123 124
```

JSONの入口は`GET /api/analysis/observations?ids=123,124`、画面は`/compare?ids=123,124`です。読み取り専用で、本文や予想の評価、動画の保管設定を変えません。本文は全文を保持し、関連情報は上限と省略を示します。資料が大きすぎる場合は対象を減らして取得します。アプリは外部AIへ自動送信しません。

動画の長さ・映像の形式・解像度・フレームレート・音声の形式も表示します。フレームレートはファイルに記録された値で、撮影設定やスロー再生時間と同一とは限りません。新しい添付では保存時に取得し、既存の動画・音声は詳細画面から情報を取得できます。原本の変換・再送やメモの追加は不要です。期限が切れた動画は再生できませんが、取得済みの仕様は記録に残ります。仕様がない古い動画の情報は復元できません。

比較では、次の三つを分けて読みます。

| 種類 | 分かること | 分からないこと |
|---|---|---|
| 添付と技術情報 | ファイルの長さ・映像と音声の仕様、原本が残っているか | 鳴いた回数・意味・感情 |
| 飼い主のメモ | 記録された前後の状況、自分の行動、その後の様子 | 未記録の場面や日常全体 |
| 予想と評価 | 飼い主が考えた意味、合っていそう・合わなそう・未判断の理由 | 意図の正解や確率、診断 |

まず似た状況を2〜3件比べ、違う反応や反対の例を探します。次に、撮れていなかった前後やその後の反応を同じメモへ残していきます。動画を実際に確認していない分析では、見た・聞いた事実として書きません。声の高さ・抑揚・長さは「声の区間」で測ります。映像による行動の自動認識や意味検索は、その必要性と検証方法を決めてから追加します。

## 動画の分析準備と保存整理

動画は新規・期限内の既存分を期限なしで保存します。保存管理では撮影月ごとの動画の件数と容量を確認し、月を選んで個別に整理できます。削除は利用者が選び、本文は残ります。期限切れ・削除済みの動画は自動復元しません。写真と音声は従来どおり期限対象です。容量上限とバックアップは引き続き必要です。

保存済みの60秒以内の動画を選び、次のコマンドで静止画（約1秒間隔）、音声WAV、音の周波数の図、1秒と0.1秒ごとの音量、周りより大きい音の候補（声の高さ・抑揚・長さと、前後1秒の0.25秒間隔の静止画付き）、保存済みの声の区間と分類、元のメモをローカルへまとめます。添付のIDは記録の比較JSONで確認できます。

```sh
python3 scripts/prepare_analysis.py --observation 123 --media 456
```

出力は `~/Library/Application Support/project-meme/analysis/` に個人データとして保存し、Gitには入りません。実行にはアプリとDockerが必要です。音量には人声や物音も含まれ、鳴き声の検出や意図の判定ではありません。動画の基本情報が未取得なら、記録画面から先に取得してください。元動画・DB・保管設定を変更せず、コマンド自体はAIへ送信しません。選んだ資料をCodexまたはClaudeで分析できます。

[FFmpeg公式ドキュメント](https://ffmpeg.org/ffmpeg.html)の映像・音声抽出を利用しています。

## 声の区間を記録して比べる

メメが何を伝えているかを確かめるため、記録の詳細画面の「声を記録して比べる」で、動画の中の声を一つずつ区間として残します（1回10秒まで。一声ずつ区切ると比べやすくなります）。

1. 動画を開き、「音の大きい場所を表示」で0.1秒ごとの音量と、周りより大きい音の候補を出します。候補を押すと開始・終了に入り、「今の位置を開始に／終了に」「選んだ区間を再生」で調整できます。候補は鳴き声の検出ではありません。
2. 飼い主が聞き分けた**鳴き声の種類**（短い「ニャッ」、長い「ニャーオ」、「ンー」「ルルッ」など。名前は「鳴き声の傾向」画面で追加・変更できます）、鳴いた回数、**そのときの行動**（こちらを見る、食器の前にいる、しっぽを立てる など）を選びます。
3. **意味の予想**（ごはんがほしい、かまってほしい など、メメ辞書と共通）と、その区間との関係（合っていそう・合わなそう・まだ分からない）を選びます。
4. **こちらがしたこと**と**そのあとのメメ**（鳴きやんだ・満足そう／鳴き続けた／強くなった／離れた／分からない）を残します。あとで分かったら「分類・その後を書き足す」から更新できます。

保存時に、その区間の平均音量（RMS）・最大音量に加えて、**声の高さ**（基本周波数の推定、Hz）、**抑揚**（上がる・下がる・上がって下がる・下がって上がる・ほぼ平ら）、**声の長さ**を測ります。以前の区間は「声の高さ・抑揚・長さも測る」で追加できます。比較画面とJSON（`sound_notes`）には、区間・分類・その後・測定値が並びます。

### 鳴き声の傾向

メニューの「鳴き声の傾向」（`/voices`、JSONは`/api/analysis/voices`、CLIは`python3 scripts/voices.py`）で、保存した区間を両方向から集計します。

- **鳴き声の種類から見る**：その声のときの行動・状況タグ・場所・そのあと・意味の予想（合っていそう／合わなそう／まだ分からないの件数）・声の高さの範囲・抑揚の内訳と例。
- **意味の予想から見る**：その予想が付いた区間で、どの種類の声・行動・そのあとが多かったか。

件数は保存した区間の数で、鳴いた回数や日常全体の頻度ではありません。区間が5件未満または記録が3件未満のまとまりには「個別の例として見る」注意を表示します。確率・正解・感情・診断は出しません。同じ声で予想と合わない例も残し、同じ声のときに予想した対応をして、鳴きやむか・満足そうかを見ることで、少しずつ確かめます。

- 声の高さは区間で一番強い周期音（200〜1600Hz）の測定値です。人の声や物音を測る場合があり、鳴き声かどうかや種類の判定ではありません。音量は録音距離や端末で変わるため、別の動画の数値は単純に比べられません。声の高さは距離の影響を受けにくい値です。
- 鳴き声の種類・行動・その後・意味の予想はすべて飼い主の入力です。アプリが自動で分類・翻訳することはありません。
- 音声そのものは複製せず、区間・測定値・分類・メモだけをDBの`sound_analyses`・`sound_behaviors`・`call_types`へ保存します。バックアップ・復元の対象です。
- 元の動画を削除・期限切れにしても、区間とメモは記録として残ります（新しい区間は測れません）。記録自体を削除すると、分析結果も一緒に消えます。
- 同じ添付・同じ区間の再送は重複保存せず、添付ごとに50件まで、同時に測るのは1件だけです。音量の表示もPOSTで依頼したときだけ計算し、保存しません。

ローカルCLIから、飼い主が確認した区間と分類を保存・書き足しできます（既定は確認のみ、`--submit`で保存）。

```sh
python3 scripts/voice.py ~/Library/Application\ Support/project-meme/drafts/voice.json
python3 scripts/voice.py ~/Library/Application\ Support/project-meme/drafts/voice.json --submit
```

新しい区間は`{"observation_id", "media_id", "start", "end", ...}`、既存の区間への書き足しは`{"observation_id", "sound_id", ...変更する項目だけ}`。分類の項目は`call_type_id`・`call_count`・`behaviors`・`meaning`（`preset:food`や`item:辞書ID`）・`assessment`・`owner_response`・`outcome`・`observation`・`hypothesis`・`unknown`です。

測定はアプリのコンテナ内のFFmpegで、ローカルファイルだけを読み（ネットワークのプロトコルは不可）、20秒・出力量・スレッド数を制限して実行します。

## 依存関係とコンテナのセキュリティチェック

Python依存とアプリ・DBコンテナのOSパッケージの既知の脆弱性を、PR・mainへのpush・手動実行・毎週月曜の予定で調べます（OSは06:30、Pythonは12:23、日本時間）。定期実行はGitHub側の混雑などで遅れる場合があります。アプリ用と監査ツール用の両方を、バージョンとSHA-256ハッシュで固定しています。[pipのハッシュ検証](https://pip.pypa.io/en/stable/topics/secure-installs/)を参照できます。

```sh
python3 scripts/security_check.py --check-lock  # 一覧の整合性だけ、通信なし
python3 scripts/security_check.py               # 使い捨てDockerで脆弱性監査
```

Python監査へ渡すのは公開パッケージの名前・バージョンとハッシュだけです。個人の動画・写真・メモ・DB・.envはマウントしません。見つかった脆弱性や監査の失敗はチェック失敗にし、自動更新・自動マージは行いません。[pip-audit](https://github.com/pypa/pip-audit)はPython依存の監査であり、OS・FFmpeg・アプリの権限や業務処理まで安全と証明するものではありません。


OS検査は次のコマンドです。既定では現在のソースから一時イメージを作り、`--image`なら指定したローカルイメージを検査します。

```sh
python3 scripts/container_check.py
python3 scripts/container_check.py --database    # 設定済みのDBイメージを検査
python3 scripts/container_check.py --image project-meme:local
```

検査ツールTrivyはイメージdigestで固定し、更新48時間以内の脆弱性DBを取得してから、ネットワークを切ったコンテナでイメージのアーカイブを調べます。Dockerソケットや個人データは渡しません。修正版のあるHIGH／CRITICALは失敗、修正版がないHIGH／CRITICALは件数を表示します。未修正の検出がある状態で成功する場合もあるため、成功を「脆弱性ゼロ」と読み替えません。[Trivyのコンテナ検査](https://trivy.dev/docs/latest/target/container_image/)を参照できます。

アプリのベースはdigest固定のPython 3.13・Debian Trixieを使い、ビルド時にOS更新を適用します。通常アプリとテストのアプリコンテナはメモリ2GB・CPU 2・プロセス128を上限とし、ローカルのファイル解析による資源消費を抑えます。

DBはPostgreSQL 18・Debian Bookwormの公式イメージをdigestで固定し、`Dockerfile.db`でOSの修正版を適用します。更新時は候補イメージ自体を検査してから反映します。OS世代を変えると文字の並び順やインデックスへ影響するため、Bookwormを維持しています。
