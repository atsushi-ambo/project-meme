# PythonとDBの処理を追う

## 最初に読む順番

1. `app/main.py` の `entry_save`：HTTPの入口。
2. `app/schemas.py` の `ObservationInput`：受け付ける入力の型。
3. `app/services.py` の `save_entry`：DBへ保存する処理。
4. `app/models.py` の `Observation`：テーブルの構造。
5. `app/templates/detail.html`：保存したデータの表示。

## 一件の観察を保存するとき

ブラウザがフォームをPOSTすると、`read_form()`がCSRFトークンを照合します。`ObservationInput.model_validate()`は日時・文字数・タグを検証します。日本時間の入力はUTCへ変換されます。入力不正なら保存せず、入力を残したフォームを返します。

`transaction()`はSQLAlchemyのSessionを開き、成功時はcommit、例外時はrollbackします。`save_entry()`は入力をObservationへ入れ、`db.add()`で追加対象にし、`db.flush()`でSQLを実行します。flushの時点ではトランザクション全体の確定前です。

概念的には次のSQLです。値をSQL文字列へ連結せず、ドライバーへ別に渡します。

```sql
INSERT INTO observations
    (cat_id, occurred_at, timezone, location, description,
     submission_key, submission_hash, created_at, updated_at)
VALUES
    (:cat_id, :occurred_at, :timezone, :location, :description,
     :submission_key, :submission_hash, :created_at, :updated_at)
RETURNING id;
```

保存した後は303リダイレクトで詳細画面へ移動します。更新直後にブラウザを再読み込みしても、同じPOSTを送らずGETします。通信切断などの再送にはsubmission_keyを使い、同じ入力なら保存済みの結果を返します。入力のハッシュを残すことで、同じキーで異なる入力を送った場合は拒否します。

## なぜテーブルを分けるか

一つの観察にはタグや予想、添付が複数あります。文章は一つのメモへまとめます。観察をタグの数だけ複製すると、本文を編集するときにすべて直す必要があります。そのため観察本体と関連テーブルを分けます。

`observation_tags`の主キーは`(observation_id, tag_id)`の組です。同じタグを一つの観察へ二度関連づけられません。外部キーは、存在しない観察やタグを参照しないように守ります。

`dictionary_evidence`も同様です。「ごはん要求かも」という予想を、声・行動のAでは合っていそう、Bでは合わなそうと評価できます。DBの値は supports、contradicts、unknown で、画面ではまだ分からない、合っていそう、合わなそうと表示します。こちらからの合図は`interactions.cue_item_id`で別に関連づけます。声・行動の入力欄には出していません。

## 添付は二段階で保存する

本文を保存した後、ブラウザはJSONで容量予約を作り、次にファイルをPUTで送ります。ファイルのリクエスト本文を分割して読み、全体をメモリへ載せません。通常フォームにはpython-multipartを使いますが、ファイル本体は余計な一時コピーを作らないraw stream方式です。

`app/media.py`は予約量と実サイズ、ファイル内容を検証します。動画はコンテナ内のffprobeでコーデックを調べ、HEVC/H.264を許可します。画像はPillowで検証します。検証コマンドにシェルは使わず、ローカルファイル以外を参照する形式は拒否します。

ファイルの移動とPostgreSQLのcommitは一つのトランザクションにはできません。そこでpending → readyという状態を保存します。途中停止したpendingはジョブが回収します。ファイルを削除できない場合は容量予約を保持し、成功するまで容量を使っているものとして扱います。

DBは同期処理なので、asyncルートからは`anyio.to_thread.run_sync()`で呼び、イベントループを塞がないようにします。Sessionを複数スレッドから同時には使いません。

## ロックと期限

通常処理は共有の保守ロック、出力・期限整理は排他の保守ロックを取得します。小規模な初版で処理の整合性を追いやすくする設計です。競合時は409で再試行を案内します。アップロード中は期限整理が次の周期へ延期されます。

期限は画面で非表示にするだけでなく、配信ルートでも確認します。「残す」と削除はDBロックで同時変更を防ぎます。削除要求をDBへ残すので、停止しても再開できます。保守ジョブは一つのWebプロセスから約60秒ごとに実行します。worker数を増やす段階ではジョブ分離を再設計してください。

## 週の振り返りと予想連携

`app/reviews.py`が期間と集計を担当し、`GET /review/week`がJinja2の画面、`GET /api/reviews/week`が同じ内容のJSONを返します。期間は日本時間の最終日を含む7日間です。SQLの条件で実記録だけを選び、GROUP BYで件数を計算するため、文章生成による数え間違いを避けられます。メモは入力として保存された内容であり、AIに対する指示としては扱いません。

`is_sample`は本文と別のBoolean列です。文面を編集しても架空のデータが実データへ紛れ込まないために分けました。Alembicで既存の先頭マーカーを移行し、原文と通常の記録を保持します。入力スキーマにこの列を含めないので、通常の投稿からサンプル判定を変更できません。

`POST /api/observations/{id}/guesses`はブラウザと同じ`add_guesses`を使います。本文保存と予想登録は別のトランザクションで、予想だけが失敗しても本文を残し、同じ下書きで再試行できます。予想の追加では飼い主の既存の支持・不一致の評価を上書きしません。週の集計はこの評価と元の記録を並べ、意味が確定したとは扱いません。

振り返りでは`REPEATABLE READ`の読み取り専用トランザクションを使います。集計中に別の投稿が保存されても、件数と原文が同じ時点を参照します。通常の保存は従来通りで、読み取り経路からのUPDATEはDBが拒否します。[PostgreSQLのトランザクション設定](https://www.postgresql.org/docs/current/sql-set-transaction.html)を参照できます。


## 同じメモへ追記する処理と編集競合

`python3 scripts/append.py --show ID`は、`GET /api/observations/{id}`から現在のメモと`revision`を読みます。追記する下書きには、確認した版番号を`expected_revision`として保存します。新しい追記ごとにUUIDの`operation_key`を作り、通信が途切れた再送では同じ下書きを使います。`--submit`を付けると、CSRFトークン付きのローカルHTTPリクエストを送ります。

サーバーの`append_observation()`は、現在のメモへ空行と追記を足します。前後の空白を取り除いた追記と合わせて1万文字を超える場合は保存しません。日時や場所、タグ、予想は追記で変わりません。文章は`observations.description`へ一度だけ保存し、別のコメント欄は作りません。

ここで使う三つの仕組みは、役割が異なります。

| 仕組み | 防ぐこと | このアプリでの使い方 |
|---|---|---|
| 行ロック | 同じ記録へ同時に書き込む競合 | SQLAlchemyの`with_for_update()`でcat、観察の順にロックする |
| 版番号の照合 | 古い画面の内容で新しいメモを上書きすること | 読み込んだ`expected_revision`と現在の`revision`を比較する |
| 再送管理表 | 保存できたのに応答を受け取れず、もう一度追記すること | UUIDと入力のハッシュで保存済みの送信を判別する |

行ロックは保存中だけ有効です。編集画面を開いて考えている間には保持しません。その間にCodexが追記したら版番号が1から2へ変わり、まだ版番号1を送る古い画面の保存を409で拒否できます。ブラウザからの観察編集も版番号を増やすため、逆に古い版を元にしたCodexの追記も止められます。これが「楽観的な競合検知」で、利用者が版番号を入力する必要はありません。入力エラーや競合でも書いた文章を残し、最新メモを確認してからまとめ直せます。[PostgreSQLの行ロック](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)を参照できます。

`observation_appends`は追記文を保存する表ではなく、送信済みの印です。キーと、親ID・版番号・追記から作ったハッシュを保存します。同じキーと内容があれば版番号の比較より先に再送と判断するため、初回保存で版番号が増えた後でも二度追記しません。別の文章や記録に同じキーを使うと409です。親が削除中なら再送も拒否します。この表の外部キーはCASCADEなので、観察を削除すると対応する印も消えます。

メモの変更、版番号の更新、送信済みの印は同じ`transaction()`でまとめます。途中で拒否されたらrollbackしてすべて元に戻り、成功時だけcommitします。Alembicで既存の観察にも初期値1の版番号を追加します。新規投稿の再送用`submission_hash`は元の入力から計算し続けるので、DB列が増えても以前の投稿の再送は変わりません。

## 動画を「残す」指定と再送

Codex投稿の下書きでは、添付ごとの`keep`を省略できます。ユーザーが「この動画を残して」と話したときだけtrueを付け、保存完了後に`POST /api/media/{id}/keep`へ送ります。既に保存済みの同じ添付なら、動画の再送を省いて保管設定だけを確認します。本文・添付・保管設定は別の保存処理なので、途中の失敗では保存済みの部分を表示し、同じ下書きで再試行できます。

APIには「現在の値を反転」ではなく「trueにする／falseにする」を渡します。trueを二度送っても残す指定のままなので、通信の再試行で解除されません。keepを送らない場合は、アプリで変更した設定もそのままです。添付の送信キーにはkeepを含めないため、保管の指定を変えても同じ動画のコピーは増えません。

Pydanticの`StrictBool`はJSONのtrue／falseだけを受け付け、文字列`"false"`や数値0／1を拒否します。通常のboolへの自動変換では意図を取り違える可能性があるためです。[Pydanticのboolean検証](https://docs.pydantic.dev/latest/api/standard_library_types/#booleans)を参照できます。

サーバーは有効な親とreadyの添付を確認し、親→添付の順でロックします。期限切れで保管指定のないファイルの復活は拒否します。保管解除では既存の期限を変えず、期限を過ぎていれば次の整理で削除される場合があります。新たな保存領域や外部AIへの送信は追加せず、アプリの保存管理からも操作できます。


### 日本語フォームの文字数と送信容量

文字数とHTTPで送るバイト数は異なります。日本語・絵文字をHTMLフォームのURLエンコードで送ると、1文字が最大12バイトになります。1万文字を受け付けるため、通常フォームの受信容量と解析時のフィールド上限を128KiBに揃えました。JSON APIは64KiB、添付は既存の別上限です。Pydanticの1万文字制限や項目・個数の検証も併用し、容量制限だけを入力規則の代わりにしません。


## 既存の観察を比較用JSONへまとめる

`python3 scripts/analyze.py --ids 123 124`は、127.0.0.1へ接続するLocalClientから比較APIをGETします。処理は、CLI → HTTPルート → 読み取り専用transaction → `app/analysis.py`の`build_comparison()` → SQL → Pythonのdict → JSONの順です。ブラウザの`/compare`も同じdictをJinja2へ渡すので、画面とアシスタント向け資料で規則を共有できます。

`parse_ids()`はカンマ区切りの文字列を、ASCIIの正整数1〜5件へ変換します。全角数字・重複・負数・BIGINTの範囲外を拒否します。SQLへは整数の一覧をパラメータとして渡し、取得後にIDから行を引くdictを作って選択順に並べます。対象のどれかがサンプル・別の猫・削除中・存在しない場合は資料全体を拒否します。

観察のメモは全文です。タグ、予想と評価理由、旧補足、添付を別々に取り出し、元の記録や辞書のURLを付けます。関連情報には件数・文字数の上限と省略フラグを付けます。資料全体が900KBを超えたら対象を減らしてもらい、通常メモを勝手に切り捨てません。

取得は`REPEATABLE READ, READ ONLY`なので、メモと関連が同じDB時点を参照し、この経路から更新できません。GETは保存済み仕様だけを読み、動画の解析を起動しません。本文を読んだだけでは映像・音声を確認したことにならないため、出典と分析未実行を明示します。予想の評価や保管設定も変えません。

## 動画の仕様をJSONBへ保存する

ffprobeの出力は映像・音声のストリームを含むJSONです。`app/media_info.py`は必要な項目だけを取り出し、文字列の数値や分数のフレームレートをPythonの数値へ正規化します。例えば`120/1`は120fps、`30000/1001`は約29.97fpsです。型が違う、値が範囲外、分母が0、NaNや無限大の場合は不明とします。GPS・任意タグ・ローカルパスはキャッシュへ入れません。

保存する小さなdictの形は次のとおりです。仕様の例であり、メメの実動画の計測値ではありません。

```json
{
  "version": 1,
  "duration_seconds": 12.5,
  "video": {"codec": "hevc", "width": 3840, "height": 2160, "fps": 120},
  "audio": {"codec": "aac", "channels": 2, "sample_rate": 48000}
}
```

`media.technical_info`のJSONBは、このdictをPostgreSQLへ保存する任意列です。未取得ならNULL、音声なしならaudioがnullになります。構造はversionで区別できます。メモ・親・状態・期限・根拠の関連は通常の列と外部キーで管理し、添付一件から導く小さな仕様だけをJSONBへまとめます。[PostgreSQLのJSON型](https://www.postgresql.org/docs/current/datatype-json.html)を参照できます。

新しい添付は内容検証の結果からキャッシュを作り、readyと一緒にコミットします。既存添付は画面のボタンかCSRF付きの`POST /api/media/{id}/info`で補充します。同じ要求を再送してキャッシュがあればそのまま返すため、原本を変換したり繰り返し解析したりしません。原本が期限削除された後にも仕様が残っていれば、「以前に保存した仕様」として参照できます。本文・期限・keepを変更する処理ではありません。

`app/processes.py`は`Popen`の出力を少しずつ読みます。`subprocess.run(capture_output=True)`で全出力を受け取ってから長さを見る方法では、調べる前に大きなメモリを使ってしまいます。今回は標準出力131072バイトと15秒に制限し、超過時は子プロセスをkillしてwaitで回収します。入力はサーバーの保存パス、引数は固定配列で渡し、シェルや外部URLを使いません。[ffprobeのJSON出力と項目選択](https://ffmpeg.org/ffprobe.html)を参照できます。

## パッケージの固定・ハッシュ・脆弱性監査

バージョン固定は「どの版を使うか」、SHA-256固定は「その版のどの配布物を受け入れるか」を確認します。pipの`--require-hashes`は推移依存も含むハッシュ指定と、取得した配布物の一致を確認します。`--only-binary=:all:`はwheelだけを受け付け、ソース配布物のインストール時ビルドを避けます。ハッシュが一致しても、その版に脆弱性がないとは限りません。[pipの説明](https://pip.pypa.io/en/stable/topics/secure-installs/)を参照できます。

`scripts/security_check.py --check-lock`はファイルを読むだけで、アプリ用と監査ツール用の固定・ハッシュ・直接依存の整合性を確認します。監査モードは検証済みlockの内容だけを一時ファイルへ固定してDockerへ読み取り専用マウントし、pip-auditで公開Python依存の既知の脆弱性を調べます。.envや個人の動画・メモ・DBは渡しません。`try/finally`でこの実行のコンテナを片付け、失敗・中断・タイムアウトを完了扱いにしません。

pytestは正しい保存や不正入力の拒否、依存監査はPython依存の既知の問題を確認する、という異なる役割です。OS・FFmpegや未知の脆弱性、独自の権限・整合性をすべて一つの検査で確認できるわけではありません。定期監査で新しく公開された情報を確認し、更新後のアプリとDBは分離テストと復元テストで確かめます。


### OSパッケージとPythonパッケージを別に検査する

ffmpegやOSライブラリはaptから入り、requirements.lockだけの監査には出てきません。`scripts/container_check.py`はdocker saveでイメージの内容を一時アーカイブへ取り出し、固定したTrivyへ読み取り専用で渡します。脆弱性DBの取得時だけ通信し、実際のアーカイブ検査はネットワークを切ります。Dockerソケットを渡す必要はなく、私用メディアのbind mountも含みません。

結果のOS・形式・更新日時を検証してから、修正版があるHIGH／CRITICALで失敗を返します。修正版がない検出は件数を残します。「成功」はこの基準で止める問題を検出しなかったという意味で、未知の問題や未修正の検出まで消えたことにはなりません。`--image project-meme:local`なら既存のローカルイメージ、引数なしなら現在のソースから新しい検査用イメージを作ります。

Composeのメモリ・CPU・プロセス数の上限は、正しい処理でも大量の資源を使わないための制限です。ファイル単位の時間・出力量と併用し、画像の画素数や入力の文字数・範囲はさらにサーバーで検証します。

### 検査に失敗したとき、どこまで進んだか

update.pyでは検査を済ませてからアプリを止めます。DBコンテナの更新を始める直前に段階を保存し、失敗や中断があればアプリを止めた状態で復元用のバックアップを残します。外部コマンドの成功と途中停止を区別して、DBの状態が不明なのに処理を続けない例です。単体テストは実コマンドの代わりに失敗を起こす関数を渡し、検査失敗では停止・DB操作・バックアップの書き換えがないことを確認します。
